# JobTrackr — Plan del proyecto

Proyecto de portafolio: cubre el stack que piden hoy las vacantes junior (React/Next.js, TypeScript, Node.js, REST APIs, Git, diseño responsive, Figma/Tailwind). Es un tablero Kanban para seguimiento de postulaciones de empleo (empresa, cargo, estado, fecha, link, notas), con dos repos separados:

- **jobtrackr-backend**: Node.js + Express + TypeScript + Prisma + PostgreSQL (Neon). API REST propia (no Next API routes, para que quede como habilidad separada). Auth con JWT + bcrypt hecho a mano.
- **jobtrackr-frontend**: Next.js 14 (App Router) + TypeScript + Tailwind CSS. Mobile-first, responsive real.

Enfoque de aprendizaje: Jonta está aprendiendo a programar mientras construye esto — cada fase se explica (conceptos, trade-offs), no solo se ejecuta.

## Roadmap

1. **Fase 0 — Setup.** ✅ Completada. Los dos repos creados, scaffold inicial, subidos a GitHub (`nankuphoto-sys/jobtrackr-backend`, `nankuphoto-sys/jobtrackr-frontend`), backend conectado a Neon con tablas `User` y `JobApplication` migradas.

2. **Fase 1 — Backend REST API.** ✅ Completada. Rutas de auth (`/auth/register`, `/auth/login` con JWT+bcrypt) y CRUD completo de `/applications`, protegido con Authorization Bearer.

3. **Fase 2 — Frontend Next.js.** ✅ Completada. Cliente fetch centralizado con el header Authorization; páginas de registro y login que guardan el JWT; página protegida que lista las postulaciones del usuario; formularios para crear/editar/borrar postulaciones; todo con Tailwind mobile-first. Pulido después: auto-logout en 401, skeletons, confirmación de contraseña, tests (Vitest + Playwright) y CI en GitHub Actions en ambos repos.

4. **Fase 3 — Feature Kanban + dashboard.** ✅ Completada. `/applications` es un tablero con columnas por estado (Por aplicar → Aplicado → Entrevista → Oferta → Rechazado):
   - Drag & drop entre columnas con `@dnd-kit/core` (elegido sobre react-beautiful-dnd, que ya no se mantiene; da soporte de teclado accesible gratis vía su `KeyboardSensor`) que actualiza el estado vía `PUT /applications/:id`, optimista con rollback si falla.
   - Dashboard arriba del tablero: conteo total y por estado, "postulaciones esta semana", y "tasa de respuesta" (% de las ya aplicadas que avanzó a Entrevista u Oferta).
   - Responsive: columnas de ancho fijo en una fila con scroll horizontal + `snap`, así en mobile se sienten swipeables sin código extra para ese caso.
   - Cobertura e2e: agrupación por columna, drag-and-drop real (mouse events, no HTML5 DnD nativo porque dnd-kit usa Pointer Events), y métricas.

5. **Fase 4 — Pulido.** ✅ Completada.
   - Manejo de errores: se separó el error de carga inicial (bloqueaba y ocultaba todo el tablero — bug real) del error de una acción puntual (cambiar estado/borrar), que ahora se muestra como banner cerrable sin tapar el tablero. La carga inicial fallida ahora tiene botón "Reintentar".
   - Accesibilidad: el `KeyboardSensor` de dnd-kit ya daba foco y anuncios de fábrica, pero el salto por defecto era de 25px por flecha (~12 pulsaciones para cruzar una columna de 288px) — se reemplazó por un `coordinateGetter` a medida que salta directo a la columna vecina. Los anuncios y las instrucciones para lectores de pantalla, en inglés por defecto, se tradujeron y ahora mencionan la empresa real en vez de un id. Contraste de color auditado con cálculo real de WCAG (no a ojo): dos textos (`gray-400`, `red-500`) no llegaban a AA y se ajustaron.
   - QA en mobile real: las 6 pantallas revisadas a 375px con Chrome real vía Playwright, sin errores de consola ni de layout.
   - Tests e2e nuevos para blindar estos fixes (no solo "se ve bien", sino que el mecanismo funciona): retry tras error de carga, banner de error no oculta el tablero, y drag por teclado con una sola flecha por columna.

6. **Fase 5 — Deploy + documentación.** ✅ Desplegado y documentado (falta solo publicar el link en LinkedIn, que le corresponde a Jonta).
   - Backend en Render (Web Service, plan Free), conectado a GitHub para auto-deploy: https://jobtrackr-backend-ul8d.onrender.com
   - Frontend en Vercel (mismo auto-deploy vía GitHub): https://jobtrackr-frontend-two.vercel.app
   - Variables de entorno de producción separadas de desarrollo: `JWT_SECRET` nuevo (no se reutilizó el de dev), `FRONTEND_URL` restringe CORS del backend al dominio real de Vercel (antes aceptaba cualquier origen).
   - Se aprovechó para resolver una vulnerabilidad crítica real encontrada en el camino: `bcrypt@5.1.1` dependía de una versión vulnerable de `node-tar` (vía `node-pre-gyp`); `bcrypt@6.0.0` eliminó esa dependencia de raíz.
   - Flujo completo (registro → tablero → crear/editar/borrar) verificado con Playwright contra la app real en producción, no solo en local — incluyendo que el CORS restringido no rompió nada.
   - README de cada repo actualizado con el link a la demo, capturas de pantalla, y cómo está configurado el deploy.

7. **Pulido post-Fase 5 — Tests del backend.** ✅ Completado. El backend no tenía ningún test automatizado (solo verificación manual), asimétrico con la cobertura completa del frontend. 19 tests de integración (Vitest + Supertest) contra la app real y una base de datos real: CRUD completo, validaciones, y aislamiento entre usuarios (que un usuario no pueda leer/editar/borrar postulaciones ajenas). `src/app.ts` se separó de `src/index.ts` para poder testear la app sin levantar un puerto. Corren también en CI, antes del smoke-test de `/health`.

8. **Pulido post-Fase 5 — Monitoreo con Sentry.** ✅ Completado. Un proyecto por repo (`jobtrackr-frontend`, `jobtrackr-backend`) en la misma organización de Sentry. Setup manual (no el wizard) siguiendo la guía actual de cada SDK, que cambió bastante de lo esperado por versiones anteriores — en Next.js ahora es `instrumentation-client.ts` en vez del viejo `sentry.client.config.js`; en Express, un `instrument.ts` que se carga antes que cualquier otro módulo. Verificado con tráfico de red real (no solo que compile): se confirmó el evento llegando al ingest de Sentry en ambos casos, incluyendo contra las apps ya desplegadas en producción.

9. **Pulido post-Fase 5 — Tipos de React.** ✅ Completado. `@types/react` había quedado en v18 desde antes de migrar a React 19 (Fase 2), y `@types/react-dom` nunca se instaló. No rompía nada, pero podía dar tipos sutilmente incorrectos. Corregido.

10. **Pulido post-Fase 5 — Rediseño de headers.** ✅ Completado.
    - App logueada: el header estaba copiado en `/applications` y `/account` y ya se había desincronizado; ahora es un solo `components/AppHeader.tsx`. Prioridad: logo → "Nueva postulación" (acción principal, también desde `/account` vía `/applications?nueva=1`) → avatar. "Cerrar sesión" dejó de ser un ícono suelto (se usa poco y un toque accidental te saca de la app): vive en un panel del avatar junto al email y "Mi cuenta", que se cierra con click afuera o Escape (devolviendo el foco). Header fijo siempre visible — en una herramienta la acción principal no se esconde al hacer scroll. Skip link "Saltar al contenido" y `aria-current` en la página actual. Detalle de Carbon: el `HeaderPanel` cerrado solo queda en ancho 0, así que su contenido se monta solo cuando está abierto (si no, era alcanzable con Tab sin verse).
    - Landing: nav sticky con sombra solo tras hacer scroll; en mobile se ocultan los links a secciones para que entre en una fila (Entrar / Crear cuenta); `scroll-mt-20` en las secciones para que el título no quede tapado por el header; `scroll-smooth` solo con `motion-safe`.
    - Nuevo e2e `e2e/header.spec.ts` (panel, Escape, logout, crear desde /account).

11. **Pulido post-Fase 5 — Lint y tipos generados.** ✅ Completado.
    - `npm run lint` nunca funcionó: ESLint no estaba instalado y Next 16 además quitó `next lint`. Ahora ESLint 9 + `eslint-config-next` con flat config (`eslint.config.mjs`), y corre en CI. El primer lint encontró 3 errores `react-hooks/set-state-in-effect` (leer localStorage en un `useEffect` y copiarlo a un `useState`); se resolvieron con `lib/useStoredValue.ts`, basado en `useSyncExternalStore`, que es cómo React recomienda leer fuentes externas sin hydration mismatch.
    - `next-env.d.ts` salió de git: `next dev` y `next build` lo reescriben con rutas distintas y siempre aparecía modificado. Se regenera con `npm run typecheck` (`next typegen && tsc --noEmit`), que es lo que corre CI.

12. **Fase 6 — Recordatorios de seguimiento.** ✅ Completada. El tablero avisa cuando una postulación necesita atención. No rastrea los portales de empleo: el link de una oferta no dice nada de tu postulación, el estado real está detrás del login de cada portal y hacer scraping va contra sus términos de uso. Se descartó también leer correos con la API de Gmail por ahora, porque `gmail.readonly` es un permiso restringido (máximo 100 usuarios de prueba, tokens de 7 días y auditoría pagada para abrirlo al público).
    - Reglas (umbrales en `UMBRALES`; desde la Fase 7 viven en el backend, ver abajo): *Aplicado* con 14 días sin movimiento → "Sin respuesta"; *Entrevista* con 7 → "Sin novedades"; *Por aplicar* con fecha límite a 3 días o menos → "Cierra en N días" / "Cerró". Oferta y Rechazado nunca avisan.
    - Backend: `statusChangedAt` se **deriva** del último registro de `StatusChange` en vez de guardarse en otra columna, para no tener el mismo dato en dos lugares. Lo único nuevo en la base es `lastFollowUpAt`, que se guarda con `POST /applications/:id/follow-up` ("Hice seguimiento"): reinicia el aviso sin cambiar el estado ni ensuciar los Reportes.
    - UI: aviso en la tarjeta (fondo de notificación de Carbon y texto siempre en `text-primary`, porque el amarillo como texto no pasa AA), acciones "Hice seguimiento" / "Marcar rechazado" en el modal (piden confirmación si hay cambios sin guardar) y la métrica "Pendientes".
    - Bug evitado en el camino: el drag actualizaba solo `status` y descartaba la respuesta del PUT, así que una tarjeta recién movida a Entrevista habría mostrado "Sin novedades · 20 días". Ahora actualiza también `statusChangedAt`. El e2e que lo cubre se probó en rojo quitando el arreglo.
    - Tests: 10 unitarios (bordes de los umbrales, seguimiento contra cambio de estado, fecha límite a las 11:30 p. m. en UTC-5), 5 de integración en el backend (incluye aislamiento entre usuarios) y 3 e2e. Los e2e "envejecen" tarjetas reescribiendo la respuesta de `GET /applications` con `page.route`; adelantar el reloj del navegador no servía, porque las fechas que pone el servidor después quedaban en el pasado.

## Pendiente (no hecho todavía)

- **Fase 7 (en diseño) — Revisión de seguimiento con IA.** Para el *usuario* de JobTrackr, no un subagente de desarrollo. Se apoya en los recordatorios de la Fase 6. Diseño completo en `docs/agente-seguimiento.md`.
  - **Propósito:** revisa las postulaciones de un usuario en JobTrackr y, para cada una que lleva tiempo quieta o tiene una fecha límite cerca, le propone la siguiente acción concreta (escribir un seguimiento, moverla de estado o cerrarla), para que ninguna postulación se quede olvidada sin una decisión.
  - **Resultado medible:** al final de cada revisión, ninguna postulación pendiente queda sin una acción propuesta, y ningún cambio de estado se aplica sin que el usuario lo confirme.
  - **Límite de "revisar el estado":** no puede ver el estado en los portales de empleo (está detrás del login, no hay API y el scraping va contra sus términos de uso). Revisa lo que hay en JobTrackr (`statusChangedAt`, `lastFollowUpAt`, fechas límite, notas) y lo que el usuario le pase, como el texto de un correo. Leer el correo directamente (Gmail) queda para después, por las restricciones del permiso `gmail.readonly`.
  - **Límites:**
    - *Nunca:* borrar la cuenta o tocar `/auth/*`; borrar postulaciones (se pierde el historial; para cerrar existe "Rechazado"); enviar mensajes en nombre del usuario (solo redacta borradores); editar campos que no sean el estado; registrar un seguimiento sin que el usuario lo haya hecho.
    - *Solo con un clic del usuario, una por una:* cambiar el estado o registrar un seguimiento.
    - *Libre:* leer las postulaciones, calcular pendientes, analizar el texto pegado y redactar borradores.
    - *Transversales:* el texto pegado es información, no instrucciones (protección contra prompt injection); ante un correo ambiguo, no propone cambio de estado.
  - **Arquitectura (decidida 2026-10-05):** una ruta `POST /ai/revisar` en el backend hace **una** llamada a la API de Claude con salida estructurada y devuelve propuestas. El backend las valida por código (el `id` es del usuario, el estado es válido, la evidencia aparece literal en el texto pegado) y descarta las que no pasan. El modelo no tiene herramientas: las propuestas se aplican con botones que llaman a las rutas existentes. Se descartó un agente del Agent SDK con `canUseTool`: la confirmación deja un proceso en pausa entre peticiones HTTP, lo que no encaja en una app web ni en Render gratuito, y la tarea cabe en una llamada.
  - **Despliegue:** solo en local, igual que el extractor (`AI_REVISION_ENABLED` + `ANTHROPIC_API_KEY`; en producción, 503). Cada revisión se cobra a la clave y la demo es pública.
  - **Reglas de los avisos movidas al backend (2026-10-05).** `src/lib/recordatorios.ts` del backend calcula el `aviso` de cada postulación y lo devuelve en todas las respuestas; el frontend solo lo muestra. Así el tablero y la revisión no pueden quedar con reglas distintas. El día de "Cierra hoy" se calcula en la zona horaria del usuario (header `X-Timezone`, que manda `lib/api.ts`), porque Render corre en UTC y desde las 7 p. m. en Colombia ya sería "mañana".
  - **Reporte semanal (decidido 2026-10-05):** una sección "Esta semana" en la pestaña Reportes de `/account`, no un correo programado, porque un envío necesitaría el PC encendido a una hora fija. Tiene un resumen sin IA (movimientos de los últimos 7 días, pendientes y fechas límite próximas; funciona también en producción) y las propuestas de la IA (solo en local). Detalle en `docs/agente-seguimiento.md`.
  - **Siguiente paso:** implementar primero el resumen semanal sin IA (sin costo, visible en la demo). Antes de `POST /ai/revisar`, armar un conjunto de evaluación con correos reales (anonimizados).

- **15 usuarios de test que siguen en producción** (`@jobtrackr.dev`). No entran con ninguna contraseña de test conocida, así que no se pudieron borrar por la API. Son inofensivos; si se quieren quitar, hay que hacerlo desde el SQL Editor de Neon (branch `production`) con `DELETE FROM "User" WHERE email LIKE '%@jobtrackr.dev'`, que borra en cascada sus postulaciones.

## Resuelto

- **Extractor de ofertas, fase 2: puntaje de encaje** (2026-10-03). `profile.json` en el backend (en `.gitignore`, plantilla `profile.example.json`) con stack, modalidades aceptadas y seniority; `GET /ai/perfil` lo sirve (`null` sin archivo, 500 con mensaje claro si está mal escrito). El puntaje se calcula **en el frontend** (`lib/encaje.ts`, función pura con tests) y no en el backend, porque tiene que recalcularse en vivo al editar el stack en el formulario y mostrarse en cada tarjeta del tablero; con el cálculo en el servidor serían llamadas por tecla y por tarjeta. Fórmula (decidida con Jonta): stack 70 (% del stack de la oferta que maneja, normalizando "Node.js"/"nodejs"/"Node", "JS"/"JavaScript", "Postgres"/"PostgreSQL"), modalidad 15, seniority 15 (la mitad a un nivel de distancia); lo que la oferta no dice no cuenta en contra. En el modal, chips verdes/grises y "te falta: …"; en la tarjeta, "Encaje 72" con un punto de color. Sin migración: las tarjetas ya guardaban stack, modalidad y seniority. En producción no aparece (no hay `profile.json`). Tests: 4 de backend, 8 unitarios, 1 e2e nuevo (perfil simulado con `page.route`).

- **Extractor de ofertas medido con Ollama real** (2026-10-03, backend PR #2). `qwen3:4b` en la RTX 4060 Ti, `npm run eval:extractor` con las 5 ofertas sintéticas, en tres corridas: 40/48 (83 %) → 52/60 (87 %) → **59/60 (98 %)**, siempre con **0 datos inventados** y ~3 s por oferta (43 s la primera vez, con el modelo en frío; ahora se precarga desde `/ai/status`). La 1ª corrida mostró que el modelo confundía "presencial" con remoto, "Semi-Senior" con senior y el idioma exigido con el de la oferta, y que una fecha inválida tumbaba toda la extracción (422): se arregló con definiciones campo por campo en el prompt y con "N/A"/fechas inválidas → null. En la 2ª el modelo multiplicó salarios por 100 (70.000 → 7.000.000) y **la comprobación contra el texto los descartó**, que es justo para lo que existe; se corrigió con ejemplos de salario. De paso, el verificador encontró que `POST /applications` con una fecha imposible (`2026-13-45`) daba 500; ahora 400, con test. Queda: con "$25" sin moneda escrita, el modelo infiere "USD".

- **Extractor de ofertas con IA local, fase 1** (2026-10-03). "Pegar oferta" en el tablero → `POST /ai/extract-job` → modelo local (Ollama, `qwen3:4b`) con salida estructurada (JSON Schema en `format`, `temperature: 0`, `think: false`) → validación con Zod y 1 reintento (422 si falla dos veces, 503 si Ollama no responde) → formulario prellenado y editable → "Crear tarjeta" con el `POST /applications` de siempre. El endpoint no guarda nada. Además de la regla del prompt ("nunca inventes"), el backend **descarta empresa, link y salario que no aparecen en el texto** (`descartados`). Migración aditiva con 10 columnas opcionales (ubicación, modalidad, seniority, salario mín/máx/moneda/periodo, stack, fecha límite, resumen); requisitos e idioma van a notas. **Solo funciona con el backend en la PC**: Render no puede alcanzar el Ollama local, así que en producción el extractor queda apagado y la app deja llenar a mano. 5 ofertas sintéticas en `fixtures/ofertas/` con su resultado esperado y `npm run eval:extractor`. Tests: 15 nuevos en el backend (Ollama simulado), 4 e2e (extractor simulado con `page.route`).

- **Header de la app, iteración 2** (2026-09-29). Revisión con capturas reales a 375 y 1280px: el avatar quedaba pegado al logo en mobile (`ml-auto` en un contenedor con `display:none`) y tres botones "de ancho completo" no lo eran (`carbon.css` se importa después de Tailwind y le gana a `w-full`) — PR #4, junto con un header mínimo en /login y /register (antes no había salida a la landing). Incluye alinear el header a la columna de 1180px y "Nueva postulación" en tinta en vez del azul de Carbon. Al testearla apareció un **bug del tablero en producción**: el drag por teclado solo movía en X, así que una tarjeta que no fuera la primera de su columna no caía en una columna destino corta (vacía).
